# Query — 知识查询（vault 版）

核心理念：好的回答本身就是知识，应回流到 wiki 中。一次对比分析、一个发现的关联、一段综合论述——这些不应消失在聊天记录里，而应像摄入的源文档一样在知识库中持续积累。

## 前置条件

- 已 Read AGENTS.md 查看规范

## 步骤

1. **从 `~/.llm_wiki.setting.json` 读取配置**（含 wiki 根路径、`storage_type=vault`），获取 INDEX.md 路径 → 解析注册表和路径映射

2. **两阶段搜索相关页面**
   - **结构化粗召回**：从 INDEX.md 页面注册表中按标题、别名、标签、关联、摘要匹配候选页；优先保留直接命中问题主体、问题类型和已知关联链的页面。
   - **正文补充召回**：当结构化召回不足、问题涉及正文细节，或标题/别名未覆盖用户措辞时，用 `grep`/`rg` 在 `wiki/` 目录下搜索关键词补充候选；搜索结果必须回到 INDEX.md 校验页面是否属于当前 wiki。
   - **轻量重排**：综合标题/别名命中、标签命中、关联路径、正文搜索命中、页面类型和证据覆盖度排序。Source 提供一手证据，Entity/Concept 提供定义和事实，Comparison/Overview 提供综合判断。

3. **按证据覆盖读取页面**
   - 默认 Read 3-5 个最相关页面（直接用 Read 工具读 `.md` 文件，路径来自 INDEX.md 注册表）
   - 若问题覆盖多个实体/概念、需要对比，或初读后证据不足，可扩展到最多 8 个页面
   - 读后若发现关键证据缺口，回到步骤 2 追加召回；不要只因标题不匹配就放弃正文相关页面

4. **综合回答**（引用 wiki 页面时使用 `[[目标页面路径]]`），回答形式根据问题类型灵活选择：
   - Markdown 文档（默认）
   - 对比表格（Comparison）
   - 幻灯片（Marp）
   - 图表（matplotlib / mermaid）

5. **归档判断与推荐**

   根据回答类型判断是否推荐归档：

   | 回答特征 | 归档推荐 | 页面类型 |
   |---------|---------|---------|
   | 对比了 2+ 实体或概念 | 推荐归档 | Comparison |
   | 综合了 3+ wiki 页面进行综述 | 推荐归档 | Overview |
   | 简单事实查找（答案来自单页） | 不归档 | — |
   | 解释已有页面内容 | 不归档 | — |

   当判断为「推荐归档」时：
   - 主动向用户推荐，展示拟创建的页面标题和存放目录
   - 用户确认后立即创建页面、补充交叉引用、更新 INDEX.md 和 LOG.md
   - 创建页面：在 `wiki/comparisons/` 或 `wiki/overviews/` 用 Write 创建 `.md`（含 YAML frontmatter）
   - 归档后补充交叉引用，让新页面融入已有知识网络
   - 用户拒绝则跳过，在 LOG.md 中记录「归档: 无（用户跳过）」

6. **丰富已有页面**（无论是否归档都执行）

   检查回答是否为已有页面带来了新信息：
   - 发现了 Entity A 和 Entity B 之间的新关联 → 更新双方的「相关实体」段落
   - 为某个 Concept 补充了新的来源或解释 → 更新该 Concept 的「来源」和「详细说明」
   - 修正了某页面的过时信息 → 更新该页面内容和 frontmatter 中的「updated」

   更新方式：Read 页面 → 精确替换相关段落 → Write 回写。更新前向用户简要说明要更新哪些页面及原因。

7. **更新 INDEX.md 和 LOG.md**
   - **INDEX.md 页面注册表**：LLM 已持有 INDEX.md 全量内容，合并新增/变更行后整篇重写（Read → 合并 → Write，内容须以 `# INDEX` 一级标题开头）；仅改个别字段（如「页面总数」「最后更新」）时精确替换那一行。**不要用 append 追加新表**——append 出的表格行不会并入原表。
   - **LOG.md**：用 `cat >>` 追加日志条目。
